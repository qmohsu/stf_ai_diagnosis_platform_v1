## 第一部分:现状问题的详细分析

### 组织方式

现行架构图自上而下有三层红色:通道层(两个虚线框)、机制层
(两条查询路径各穿过一个缺陷带)、工件层(底部灰盒描述的根
因)。问题编号按此分层。所有数据来自 2026-07-21 缺陷扫描与
2026-07-22/23 保真度审计(TRICITY155,434 页)。

### P1 通道层:两条通道整体缺失

**P1.1 无字面检索通道。** 全系统没有任何 grep 式检索:manual
子 agent 只有 3 个导航工具;主 agent 的 `search_manual` 是
pgvector 语义检索,对标识符查询返回噪音(HARNESS-15 实测,
故而当时从子 agent 移除)。后果:"哪里提到过煞車油"这类定位
问题只能靠标题树猜;更严重的后果见 P1.2。

**P1.2 无缺席验证纪律。** agent 宣称"手册没有 X"之前不需要
任何证据。cross-006(v2.2 最低分 0.483)是完整事故样本:agent
把快速索引的 `-` 标记读作"手册没有 P0335 的自我诊断条目",
并把通用 ECU 说明外推成错误的 fail-safe 结论(跛行模式 vs 手
册真实的無法運轉)——判分 judge 原话"技师会被彻底误导"。
这是对维修场景最危险的失败模式:自信的存在性否定。

### P2 机制层:两条现存路径各踩一个缺陷带

**P2.1 DTC 快速索引的原料是标题,而 13/22 个码没有标题。**
HARNESS-28 建立的码→slug 映射只能映射到"标题",但 P0335 等
13 个码的排查程序在 md 里是无标题孤儿块(第 8 章逐码程序被
marker 吞进上方垃圾 NOTE 标题的区间)。映射不到就填 `-`,而
`-` 被 agent 当成缺席证据(P1.2 的直接燃料)。

**P2.2 标题树浏览无类型标签,重名靠子串赌运气。** 37 组重名
标题(引擎 ×6、電裝系統 ×5、電路圖 ×8…);`_match_section`
的第三策略是子串匹配**静默返回第一个命中**;52% 的章节
(379/726)低于默认目录深度 3,agent 只看到"...N more"占位。
历史事故:HARNESS-24 之前 agent 想读刹车放空气步骤,读成了
同组件的拆卸章节——没有 node_type 标签,任务消歧只能靠中文
标题语感。

**P2.3 read 的区间由 `#` 级数推导,而级数与文档逻辑无关。**
`include_subsections` 按标题级数嵌套取区间,但 marker 的级数
来自逐页字体聚类:`無法起動/起動困難` 的正文全部流入同级兄弟
标题,该节区间为空(全书 12%,87/726 节是这样的空壳);
`自我診斷功能表` 被倒挂进"喇叭不會響"的父链。agent 读到空
内容,再次得出"手册没有"(P1.2 的另一条燃料线)。

### P3 工件层:根因,一个耦合工件

**P3.1 存储与索引耦合:标题即地址。** 章节的可达地址(slug)
直接从标题文本生成——标题被转换器弄丢,内容就没有地址,从导
航世界里消失。P2.1/P2.3 都是这一条的具体表现。

**P3.2 索引是运行时现场解析,不存在质检位置。** 每次工具调
用现场解析标题树,没有构建环节,因此没有任何"发布前拦截"的
机会——全部缺陷只能等生产里的 golden 分数暴露(cross-006 潜
伏了一年)。

**P3.3 转换引擎本身不可靠,且无引擎可靠。** marker 1.10:
1212 个原始标题中 40% 是视觉噪音(注意/警告横幅、流程图记号、
图注),层级随机。四引擎对比(PyMuPDF 逐行基准):

| 引擎 | 字符召回 | 数值召回 | 灾难性丢失模式 |
|---|---|---|---|
| marker 1.10(现网) | 92.7% | 83.7% | 图文混排页文字丢失 |
| marker 2.0 | 89.7% | 81.7% | 全面垫底;但退化时存页面图 |
| MinerU 3.4 medium | 94.5% | 83.7% | **48 个表格条目静默输出为空**(规格表、刹车分解图、P0335 区) |
| MinerU 3.4 high | — | — | 共享 GPU 上内部超时,不可重复 |
| Docling | 79.6% | 99.8% | 丢弃无法归类的散文段(20%) |

结论:没有引擎独立满足 100% 召回;每个引擎的丢失都是静默的。

**P3.4 换引擎会打碎评测基线。** 30 条 locked golden 的引用
(`golden_citations`/`expected_recall_slugs`/`expected_tool_trace`)
全部绑定现行 slug——slug 又派生自标题——引擎一换,slug 全变,
专家人力构建的评测资产失效。这条把系统锁死在 marker 1.10 上。

### 因果链总结

```
根因:一棵由视觉猜测得来的标题树,同时充当了
     结构(P2.3)、地址(P3.1)、索引原料(P2.1)三种角色
  → 且没有质检环节可以拦截它的错误(P3.2)
  → 且没有绕开它的第二通道(P1.1)
  → 且没有防止错误升级为存在性否定的纪律(P1.2)
  = cross-006 式事故:内容存在,agent 自信地说"没有"
```

## 第二部分:新架构的逐步实现计划

### 总原则(来自规范 §0,此处重申以自足)

1. 存储与索引解耦:content.md 是纯存储,不承载结构主张。
2. 权威分工:文字来自 PyMuPDF(原生版 100% 由定义保证);
   引擎降级为可插拔的几何顾问,错了只影响排版质量,不丢内容。
3. 构造性完整 + 门禁验证:先由架构保证,再由 I0-I8 断言。
4. 索引是一等工件:构建产物、schema 校验、可重建、发布有门禁。

### Phase 0 — 字面检索地基 + 缺席纪律(= HARNESS-30a,#217)

**为什么先做**:目标图右侧两条通道(按关键词定位、缺席验证)
的地基,不依赖新索引——grep 的对象是原始内容,现行 marker md
上就能生效,立即封住 P1.2 这个最危险的失败模式。

| 步骤 | 内容 | 验收 |
|---|---|---|
| S0.1 | 新工具 `search_manual_text`:大小写不敏感子串检索,逐命中返回所在章节 slug;注册进 manual 子 agent(3→4 工具)与主 agent | 单测:命中归属、零命中语句、max_hits 截断 |
| S0.2 | 快速索引 `-` → `NOT-INDEXED(use search_manual_text)` + 目录尾部守卫说明("出现次数 >0 即存在,禁止读作缺席") | 单测:13 个未映射码全部携带新标记 |
| S0.3 | 子 agent 提示词纪律:任何"Not found / 手册没有"结论前必须 grep 关键标识符;NOT-INDEXED 永远不是缺席证据 | 提示词评审 + 定向重跑 |
| S0.4 | R1 噪音正则扩展:带编号横幅(`警 告 EWAxxxxx`/`注 意 ECAxxxxx`)、流程图记号(`OK↓`、`▲▼` 行)——现存 49 个漏网假标题 | 单测:49 个样本全部过滤,现有 193 测试无回归 |
| 门禁 | adversarial/dtc 类 golden 定向重跑无回归;cross-006 预期不再走"自信缺席"路径失败 | 分支部署 + 报告,merge 由用户定 |

覆盖目标图元素:字面全文检索框、缺席验证通道。
工作量:约 1 天(含部署验证)。

**并行项 P0-p**:三条稳定低分(lookup-005/image-006/
adversarial-006)的只读根因诊断(上次任务被终止,未完成)。
产出:每条的根因分类(索引缺陷/内容缺陷/agent 行为/判分噪音/
图片管线)——**结论直接决定 Phase 2 验收清单的构成**,必须在
Phase 2 开工前完成。约 1.5 天。

### Phase 1 — 存储管线(M1,需求 S1-S5)

**为什么第二做**:一切索引的前提是"内容 100% 在场"。本阶段
产出 TRICITY155 的新版 content.md,并把审计脚本转正为构建门禁。

| 步骤 | 内容 | 验收 |
|---|---|---|
| S1.1 | mineru 适配器:`content_list_v2.json` → 归一化条目流 `{idx, page, kind, text\|html, bbox}`(规范 §3.4 契约) | 适配器单测(fixture 页) |
| S1.2 | 文字权威抽取:PyMuPDF 逐页逐行,页眉/页码等 furniture 判定 | 与既有审计脚本(`fidelity_audit2.py`)的基准一致 |
| S1.3 | 合成器:按①阅读顺序装配,文字一律取自② | 合成产物通过 S1.6 |
| S1.4 | 区域救援:引擎输出为空的区域(实测 48 个空表)按 bbox 150dpi 渲染嵌回;**表格阶梯梯级 1 实验**:PyMuPDF `find_tables()` 直击 48 个 bbox,按"区域数值召回 + 单元格抽查"打分,达标则空表恢复为结构化表而非纯图 | 救援区域清单进构建报告;梯级 1 实验报告 |
| S1.5 | 双重表示:含可抽取文字的图区域,图与文字同时保留 | 三面图/流程图页抽查 |
| S1.6 | **I0 精确对账门禁**:基准每一行必须字面存在于 content.md,差一行构建失败;构建报告骨架(覆盖统计、救援清单、噪音样本) | I0 全绿是本阶段唯一放行条件 |
| 检查点 A | 构建报告 + P0-p 诊断结论一并交用户——这是调整 Phase 2 范围的最后时机 | 用户审 |

覆盖目标图元素:content.md + 图片(存储工件)框。
工作量:约 2-3 天。风险:MinerU 输出若在对账中暴露新的系统性
丢失,先解决保真再前进(计划内的停下条件)。

### Phase 3 — 工具层切换 + golden makeup(M3)

### 风险登记(前三项)

1. **Phase 1 对账暴露 MinerU 新的系统性丢失** → 计划内停下条
   件,先修保真;表格阶梯与救援机制是既定缓冲。
2. **makeup 不干净导致"尺子失真"** → 双轨全程在线 + A/B 均
   值比对 + 人审映射表;切换前旧管线永远可回退。
3. **judge 方差污染验收** → 所有评测门禁均以 2-3 轮均值为
   准,单条单轮波动明文不作数(写死在 S3.3)。

### 明确不做(本计划边界)

- 扫描版 PDF 的 OCR 路径:占位 #220,首本扫描件触发。
- RAG 语义通道改造:保持现状,不进本计划。
- 前端阅读器重构:仅 S4.3 小票,不阻塞。
