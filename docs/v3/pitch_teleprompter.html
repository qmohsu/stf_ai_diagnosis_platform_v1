STF V3 架构讲稿 · 提词器

① 开场定调（30 秒）

  • V3 = 我们的第一个产品化版本——不再是实验，是给真实客户用的系统
  • 一句话目标：给车队一个监控历史诊断 + AI 诊断建议的平台，未来持续长功能
  • 今天讲四件事：为什么做、路线怎么选、架构长什么样、下一步怎么走

② 为什么是现在做 V3（1 分钟）

  • 客户需求已经落定：管理 20 辆车的车队
  • 手里的 V1/V2 是研发学习版——使命已完成，不适合直接交给客户
  • 数据链路曾被硬件侧阻塞 → 我们把窗口期变成产品与数据资产建设期
  • 结论：与其改造旧版，不如并行新建产品版——V1/V2 留作测试床、最终废弃

③ 技术路线：自研 → 开源（1.5 分钟）

  • 当初自研 Agent Harness 是为了学习——loop、上下文压缩、工具编排亲手做一遍
  • 底层逻辑摸清了，自研的使命就结束了——继续维护它是负担，不是资产
  • 现在换开源 Runtime：Pydantic AI——为了维护省力、升级跟随社区
  • 选型不是拍脑袋：三轮决策看板 + 纸面深度对比之后拍的板
  • 大厂主流的 LangGraph 为什么没选——档位不同，留作远期编排层选项
  • 真正的家底全部沿用：工具组、手册知识库、金标评测

④ 产品形态与交互（1.5 分钟）

  • 交互核心：车辆是一切的锚点——车队 → 车辆 → 诊断会话
  • 上传与诊断解耦：设备传日志只入库，诊断是车辆页上的显式动作
  • 演进四阶段：初版只做 S1 一键报告，之后每阶段只加不改
  • 前端：Next.js 15 + shadcn/ui——手机电脑都走网页，移动优先
  • 诊断过程SSE 实时流式：客户看叙事进度，工程师切换透视视图

⑤ 架构分层速览（1.5 分钟 · 对着架构图讲）

  • 五层：前端 → 后端四服务 → Agent 核心 → 独立新库 → 模型层
  • 后端四服务：邀请码 Auth · 上传薄层 · 诊断编排 · 任务队列
  • Agent 核心：开源 loop + 自研Context/Memory 策略 + 沿用工具组
  • 数据：独立新库 · 8 张表——含审计黑匣子和可续跑的会话
  • 模型：默认本地 vLLM + Qwen3.6——云端只留一个对比测试口

⑥ 质量与底线（30 秒）

  • 一切改动过Golden 评测门槛——换 runtime 不掉分才放行
  • 隐私口径：VIN 暂存明文，摸清整套工作流后择机模糊化
  • 数据不出本地：诊断默认全跑在自己的 GPU 上

⑦ 路线图与可扩展性（1 分钟）

  • 近期：S2 报告内追问 → S3 车辆自由对话（护栏就位后）→ S4 异常主动提醒
  • 第二批：相似案例飞轮——每次真实诊断都沉淀为数据资产
  • 已预留：车队病历系统接口（学生项目对接）· fleet 分组 · 权限体系
  • 扩展成本已评估：加功能基本是加表加列，不动存量数据

⑧ 会上要收集的输入

  • ☐ 20 辆车的接入节奏：一次全上，还是先 2-3 辆试点？
  • ☐ 客户侧日常操作者是谁：管理者本人还是技师？（影响 UI 优先级）
  • ☐ Jetson 设备安装计划与车辆清单（品牌/型号/VIN）
  • ☐ 邀请码发放对象名单
  • ☐ 第一批验收标准：客户认什么算"诊断有用"
